# Project Brief

> Name: **Mondo** (Italian/Portuguese-adjacent: "world"). Resolved — see OQ-1, decided 2026-09-03.
> Deliberately avoids `-le` naming. Game mechanics are not copyrightable, but NYT has been
> aggressive about Wordle-derivative naming, and this project is public and open source.

## 1. What this is

A daily country-silhouette guessing game, self-hosted on `lisecki.dev`, built to be played
by a small competitive group (a company team) over lunch.

Inspired by Worldle (https://worldle.teuteuf.fr/). No Worldle code or assets are used.

## 2. Why not just use Worldle

Three gaps drive this project:

| # | Gap in Worldle | What we build |
|---|---|---|
| G-1 | Progress lives in `localStorage`, lost on browser/device change | Authenticated accounts, server-side history |
| G-2 | No groups, no shared ranking | Groups with invite codes and leaderboards |
| G-3 | No way to play head-to-head with a friend | Async challenge mode |

## 3. Non-goals (v1)

Explicitly out of scope, to keep this finishable:

- Real-time synchronous multiplayer (both players racing on a live timer)
- Mobile native apps
- ~~Anything beyond country silhouettes (no flags, no capitals, no "guess the country from a photo")~~
  — **amended 2026-09-09 for Phase 3.** This was a v1 boundary and the tournament engine crosses it
  deliberately: challenge *kinds* now include the capital city, with flags and GDP planned
  (`docs/06-tournaments.md` §5). Photos stay out — an asset pipeline with a licensing problem.
- Public global leaderboard across strangers
- Monetization, ads, analytics beyond basic error logging
- Internationalization beyond pt-BR + en

## 4. Users

- **Player** — a colleague. Signs in with a *personal* email. Plays the daily, joins a group,
  challenges people.
- **Group owner** — created the group, can rename it, rotate the invite code, remove members.
- **Maintainer** — the repo owner. Runs the puzzle-schedule generator, deploys, has GCP console access.

There is no admin UI in v1. Maintainer tasks are scripts + console.

## 5. Hard constraints

- **C-1** — The existing site (`Thinato/thinato.github.io`) is vanilla HTML/CSS/JS deployed by
  GitHub Pages. The game must not force a build step or framework onto that repo.
- **C-2** — Everything open source, including infrastructure-as-code. No secrets in the repo.
- **C-3** — The server is authoritative. The client must never be able to learn the answer early.
  This is the single most important architectural rule; see SEC-1 in `01-requirements.md`.
- **C-4** — Players use personal emails, not corporate identities. The system must never
  require, request, or store a corporate email address.
- **C-5** — Running cost must stay at or near zero at 100 players.

## 6. Decisions log

Decisions already made, with reasoning. Revisit deliberately, not accidentally.

| ID | Decision | Reasoning |
|----|----------|-----------|
| D-1 | Server-authoritative answer, delivered only after the round ends | The group is competitive and technical. A client-side answer makes any leaderboard meaningless. |
| D-2 | Firebase (Firestore + Cloud Functions v2 + Firebase Auth) | Easiest secure auth; generous free tier; the frontend can talk to it without a bundler. |
| D-3 | The whole project lives in `Thinato/mondo`, which publishes its own GitHub Pages site. Because the user site `thinato.github.io` carries the `lisecki.dev` custom domain, this project site is served at `lisecki.dev/mondo/`. | Honours C-1 by never touching the existing repo at all. One `git push` deploys. Backend, infra, tools and frontend stay in one place with one history. Revised 2026-09-03; originally the game was to ship inside the Pages repo. |
| D-4 | Callable Cloud Functions (not raw HTTP endpoints) | Auth token verification is handled by the SDK; no hand-rolled JWT checking. |
| D-5 | Google sign-in as primary provider, email-link as fallback | Personal emails are overwhelmingly Gmail. No password storage. |
| D-6 | Terraform manages the GCP/Firebase project; Firebase CLI deploys functions and rules | Terraform is good at project/resource shape, awkward at function source. Split by strength. |
| D-7 | Natural Earth as the geometry source, `world-countries` for names/translations | Both public-domain / permissively licensed and downloadable as static files. |
| D-8 | Silhouette shows the *largest landmass only*, not overseas territories | Fixes France-in-the-Atlantic and makes centroid distances honest. See `03-geo-data-pipeline.md`. |
| D-9 | Puzzle day boundary pinned to `America/Sao_Paulo` | Everyone flips at the same instant. Avoids UTC-midnight-at-21:00 confusion. |
| D-10 | Async challenges only in v1; creator plays blind | A challenge where the creator picks the country is not a contest. |
| D-11 | The puzzle day runs noon-to-noon, and `rebuildStandings` runs at **12:05** `America/Sao_Paulo`, not 00:05 | Follows from OQ-2. The nightly job must fire just after the day boundary, not in the middle of a live round. |
| D-13 | Silhouette geometry and centroids are **server-only**. `getRound` inlines one SVG path per round; there are no public shape files and no shape keys at all. | The original design shipped opaque-keyed shape shards to the client alongside a `countries.min.json` that carried each country's key — a trivial JSON lookup from silhouette to answer, defeating SEC-1 outright. With shapes held server-side there is nothing public to match against except Natural Earth itself (SEC-12). A key that is never public has no purpose, so `shapeKey` was removed from the data model entirely. Decided 2026-09-06. |
| D-14 | D-8 (largest landmass only) stays the default; exceptions are listed explicitly in `tools/overrides.json` with a `minShare` threshold and a reason. | Largest-only makes Indonesia a blob of Kalimantan and Malaysia a slice of Borneo. A distance heuristic would fix those but reintroduce France-in-the-Atlantic and Norway-with-Svalbard. An explicit, reviewable exception list is simpler, and it turns "Japan should have Shikoku" into a pull request. Ten entries at launch: ID MY NZ JP PH GB IT DK GR FJ. |
| D-12 | One shared GCP project, `lisecki-dev`, holds everything on lisecki.dev. Mondo is a tenant, not the owner. | One billing surface, one budget, one console to check — the right call for a personal domain. Accepted costs: free-tier quotas are per project and therefore shared, only one Firestore database is free, and both `firestore.rules` and Identity Platform's authorized domains are project-wide and authoritative, so a careless deploy from either side can break the other. See `05-cost.md` §5. Decided 2026-09-04, replacing `mondo-prod`. |
| D-15 | **Natural Earth stays the silhouette source.** The crawled SVGs under `assets/` are a local-only visual reference, never a build input, never shipped. | Their source site and license are unknown, so anything derived from them cannot land in a public MIT repo (C-2, NFR-9). The permissively licensed alternative (simplemaps / `world-map-country-shapes`) was checked and rejected as geometry: one 2000×1001 Robinson world map, 11 in-scope countries missing, microstates about one pixel wide, and a single world projection, which `03-geo-data-pipeline.md` §3.4 forbids. Decided 2026-09-08. **Reversed by D-69 on 2026-09-18**: the silhouettes it protected were not good enough to play. |
| D-16 | `assets/` is gitignored wholesale. | Unknown license, and coats of arms are outside the v1 brief (§3). |
| D-17 | `tools/preview.html` shows the crawled reference SVG beside each Natural Earth silhouette when the file exists locally. | The only useful thing the crawl gives us is a second opinion for tuning `overrides.json` and tolerance by eye. A clean clone sees one image per card. **Retired by D-69**: the reference is the build input now, so there is nothing to compare it against. |
| D-18 | Mondo honours the parent site's `light-mode` class and `lisecki-theme` storage key but does **not** load `lisecki.dev/theme.js`. | That script plays a sound from a relative path and paints a nine-second flash overlay; under `/mondo/` the path breaks and the flash is not a game feature. Reading the class and key delivers what FR-6.6 wants: one theme across the domain. |
| D-19 | Email-link sign-in (FR-1.1 SHOULD) is deferred past Phase 1. | Google covers the group; a second provider is a second flow to test. |
| D-20 | The schedule is seeded from the maintainer's machine with Application Default Credentials, never a key file. `VA` is excluded from the pool. | SEC-10. The Vatican has no usable polygon in world-atlas 10m (two points on a line), and the build now refuses degenerate geometry rather than emit an empty path. |
| D-21 | **No `groups/*/results` fan-out.** `attempts/{uid}_{puzzleId}` is the single source of truth; the nightly job reads attempts directly and writes per-member aggregates. | Result copies would have to be kept coherent on every join, leave, deletion and retry. Reading attempts once per night for all players (≤ players × 30 docs) is cheaper and has no consistency surface. Consequence: nothing ever renders `[removido]` — a deleted account leaves every board exactly like a leaver (FR-4.9). Revisit if historical boards are ever added. Decided 2026-09-09. |
| D-22 | **One document per membership**: `groups/{gid}/members/{uid}` carries role-in-group, join date and the precomputed windows. No `standings` subcollection. | Same readers, same writer, same key. One fewer write on every membership change and one fewer thing for rules tests. |
| D-23 | **Owner leaves or deletes account → ownership passes to the longest-standing remaining member, whatever their role, and no role is granted.** Last member leaving deletes the group and its pending invites. | A group without an owner cannot invite or remove anyone, and deleting a group with people in it would be hostile. The successor needs no role because management follows *ownership* (FR-7.5) and `requireOwner` is what gates renaming, inviting and removing. Revised 2026-09-09 after the security review: the original version promoted the successor to `organizer`, which quietly unlocked the invite-only system — an organizer could create a group, invite one player, leave, and that player was then free to create groups and invite strangers. |
| D-24 | **30-day window = the 30 puzzle days ending at the last closed day; an unplayed day scores 0; the two lowest of those 30 are dropped (FR-3.5).** 7-day and all-time drop nothing. Tiebreak = sum of `elapsedMs` over finished rounds in the window, lower wins. Ranks are competition-style (1, 2, 2, 4). | The reading under which OQ-5's "two is enough slack for a holiday" is true. FR-3.3's "visually distinct" is honoured in `played` and the today panel. `regras.html` states all of it. |
| D-25 | **Boards close at noon.** Standings cover puzzle days through yesterday (rebuilt 12:05, D-11); today is a live panel (FR-4.11). All-time advances idempotently via `allTimeThrough`. | One model for players ("o ranking fecha ao meio-dia"); exactly-once arithmetic without giant transactions. |
| D-26 | **Display-name uniqueness within a group (FR-1.3) is resolved at read time**, by `joinedAt`: earliest keeps the bare name, later ones get ` 2`, ` 3`… `updateProfile` copies the new name to the caller's member docs. | Fresh after a rename, always unique, nothing to undo. |
| D-27 | **`users/{uid}.groups: string[]`** (≤10) is the membership index and **`users/{uid}.role`** holds the role. Only functions write either; the rules' `hasOnly(['displayName','locale'])` already forbids the client. | Cheaper than a collection-group query; the role belongs with the profile. |
| D-28 | **Play access = `role !== "player" || groups.length > 0`** (FR-1.7). Losing your last group locks the game again. | "Uninvited people cannot join" stays true over time with no separate allowlist to maintain. The admin can always re-invite. |
| D-29 | **Admin bootstrap is one script run with ADC**: `tools/set-role.mjs --project lisecki-dev --uid <uid> --role admin`. Further roles are set from the dashboard; the API never grants admin. | No uid hardcoded in a public repo, reproducible (NFR-7), no console clicking. |
| D-30 | **Extra chance = reset today's attempt, keep the old one in `history`.** `recordCompletion` does not double count a day already recorded. Retries are today-only. | Today-only keeps `loadOpenPuzzle` unchanged; history keeps the cheating trail for the admin. |
| D-31 | **Admin inspection of today's guesses is available only after the admin has finished today's round**; before that: state, guess count and timings. Closed days are fully visible. | Paulo plays in the same groups; seeing colleagues' distances before finishing would be cheating by his own rules (SEC-1 spirit). |
| D-32 | **Invite tokens**: 16 chars from the FR-4.2 alphabet (32¹⁶ ≈ 10²⁴), single-use, 7-day expiry, stored at `invites/{token}`, resolvable only through `acceptInvite`. | Single-use plus unguessable means a forwarded link is at worst one wrong person, revocable, removable. **Amended by D-71 on 2026-09-20**: single-use is now one of two lives a token can have, and the half of this sentence it rests on is the half D-71 trades away. Everything else here stands — the alphabet, the length, the storage and the one resolver. |
| D-34 | **`users/{uid}` is client-readable only by its owner** (`isSelf`), not by any signed-in player. | A rules condition that mentions neither `resource` nor the `{uid}` wildcard also authorizes a **list** of the whole collection, and `groups` is an array: any signed-in account, including one FR-1.7 bars from playing, could have run `where('groups','array-contains', gid)` and read out a group's entire membership with display names, plus everyone's role — exactly what FR-4.10 forbids. Other players' names reach the client only through `getLeaderboard`, which checks membership first. Nothing is lost because the client never loads the Firestore SDK. Found by the security review 2026-09-09. |
| D-35 | **`grantRetry` and `setRole` refuse to act on the caller's own account, and `setRole` refuses to change an admin's role in either direction.** | By the time your own round is over you have seen the answer, so a self-granted retry is six free points (D-30, D-31 reasoning). Admin is granted and revoked out of band only (D-29, FR-7.6), so one admin cannot demote another through the dashboard. |
| D-36 | **The exact bearing is never sent to the client.** `getRound` and `submitGuess` return the 8-point `compass` the UI already drew; `bearingDeg` stays in the stored attempt. | An exact distance *and* an exact bearing from a guess whose centroid is public solve for the answer's centroid in closed form, so one guess plus an offline Natural Earth table named the country — functionally the centroid SEC-2 forbids shipping, and a far cheaper attack than the silhouette matching SEC-12 concedes. The UI never read the field, so removing it changed nothing on screen and a determined player must now trilaterate over several guesses. Found by the security review 2026-09-09. |
| D-37 | **No page sets a `referrer` policy.** | Putting an invite token in the query string is a mild concern, and `no-referrer` would be the obvious answer — but the Firebase web API key is **referrer-restricted** (`infra/README.md` §9, SEC-9), so sending no `Referer` would have the key rejected and break sign-in. Browsers already default to `strict-origin-when-cross-origin`, which sends only the origin off-site, and `groups.js` clears the token from the address bar with `replaceState`. |
| D-38 | **Duplicate scoring: any two scores that are ever compared come from the same card.** Normally that means one card per round, played by everyone still in; the exceptions are two-player tie-break cards. | This is an async game — nobody races anybody. Comparing scores from *different* cards would let card difficulty decide who advances; comparing scores on the same card cannot. It also makes byes trivial, collapses all five formats into arithmetic over one table, and lets eliminated players keep playing for a side ranking at no cost. Confirmed with Paulo 2026-09-09. `docs/06-tournaments.md` §2. |
| D-39 | **Tournaments, rounds and cards are top-level collections with no client access**, not subcollections of `groups`. | The cards hold the answers and `groups/{gid}` is member-readable, so one future `match /groups/{gid}/{document=**}` allow — the obvious line to write when someone wants brackets on the client — would publish every answer. Firestore also does not delete subcollections with their parent, so D-23's group dissolution would orphan them. And the client never loads the Firestore SDK, so `inGroup` would have bought nothing. |
| D-40 | **Tournament play lives in `attempts` with `mode: "match"` and no `puzzleId` field.** | FR-5.9 becomes a property of the data: the daily standings job selects on a `puzzleId` range, and a Firestore inequality filter never returns a document lacking the field (verified on the emulator). No composite index, no filter to remember, and `deleteAccount`'s existing `where uid ==` sweep already collects them. |
| D-41 | **Tournament standings are a pure fold over the round log, recomputed on every advance, never stored incrementally.** | ≤ 20 rounds. D-25's lesson: at this size a full recompute is cheaper than a drift bug, and it makes closing a round idempotent. |
| D-42 | **Cards are stored, not regenerated from a seed.** | A generator that can never change is a worse constraint than a stored document; `puzzles` set the precedent. |
| D-43 | **Tournament rounds close on the puzzle-day noon boundary, floored at 12 hours, and are advanced by the existing 12:05 job; `advanceTournament` closes one early.** | No third Cloud Scheduler job (three free per *billing account*, `05-cost.md` §3.4) and one clock for the whole game (OQ-2). The floor exists because `puzzleIdAt` names the day a puzzle *opens*, so before noon "one day later" is minutes away: without it a lunchtime tournament started at 11:50 closed at noon and forfeited everybody. The manual close is what makes a one-lunch tournament, and an automated test, possible. |
| D-44 | **Every kind scores one challenge 0–6 and a card is the sum. Total elapsed time is the default next comparator, not a universal one.** | The 0–6 scale is what makes a mixed-kind card summable, and six for a first-guess solve keeps FR-3.1's scale. Time was universal in the first draft: a knockout that resolves ties by sudden death (D-50) must be able to leave it out, or millisecond ties never happen and sudden death never fires. |
| D-45 | ~~**The shipped daily is not refactored onto the challenge-kind interface.**~~ **Reversed by D-52.** | `lib/round.ts` is live, tested and playing. A dozen lines of glue duplicated in the `shape` kind is the cheaper mistake; consolidation is Phase 4+ if ever. |
| D-46 | **A participant's display name is snapshotted into the tournament at start, does not follow renames, and is scrubbed by `deleteAccount`.** | A tournament is a historical record, unlike the live board (D-26). D-21's "a deleted account just leaves" cannot apply to a bracket, which would be left with a hole and whose standings fold reads the participant list; so the uid stays and the personal data goes. |
| D-47 | **Eliminated players may keep playing the round's card for a side ranking** (`consolation`, default on). | The card is already shared, so it costs nothing, and it fixes elimination's real social problem: after round one half the group has nothing to do at lunch. |
| D-48 | **A tournament is created from a named, built-in preset, resolved server-side and copied into the tournament document. No client-supplied settings in Phase 3.** | Paulo asked for presets rather than one default. It also deletes the hardest validation problem in the phase — without it `createTournament` must reject every incoherent corner of a settings lattice, and each missed corner reaches a player as a broken bracket. Storing the *resolved* config means editing a preset cannot alter a running tournament and user-defined presets later need no migration. |
| D-49 | **Two regimes. `aggregate` (points carry, totals decide, nobody eliminated) is offered only for `free_for_all`; the four pairing formats run `match` (the card score decides that round only, shown but never carried).** | Paulo's "points optional". The restriction is forced by D-38, not chosen: under a shared card a pairing cannot affect anyone's score, so a pairing format whose pairings also decide nothing is doing no work — `round_robin` under `aggregate` is bit-for-bit a `free_for_all` league with a fixture list that pretends the draw matters. Elimination under `aggregate` fails worse: a knocked-out player cannot accumulate, and if `consolation` lets them keep playing the bracket decides nothing. |
| D-50 | **Ties are resolved by a comparator chain and then by policy: sudden death, replay, seed, or a recorded draw. Sudden-death and replay cards go only to the tied players.** | "Keep adding challenges until someone fails" is what Paulo asked for, and it sharpened D-38 into a rule about *comparisons* rather than rounds. The cost is stated: a tie holds the round open past its noon boundary, because the tied players have to actually play. |
| D-51 | **No `attempts` document is client-readable — not even by the player it belongs to.** | The old rule allowed a player to read their own attempt, reasoning that they already knew their own guesses. They did not know `bearingDeg`, which the document stores beside `distanceKm`: together the two solve for the answer's centroid in closed form, so one guess plus one REST call named the country, and on a tournament card it named five. D-36 had removed the bearing from the *response* and stopped there. "The client never loads the Firestore SDK" is a convention of our own bundle, not a control on anyone else's HTTP client — the rule is the control. Nothing is lost: every read the game performs goes through a callable that sends the 8-point compass. Found by the Phase 3 security review 2026-09-09. |
| D-52 | **A day is a card: one challenge of every kind — silhouette, flag, capital — in a shuffled order, worth 0–18. The daily is rebuilt on `lib/card.ts`, reversing D-45.** | Paulo asked for every game type every day. D-45 was right while a day was one silhouette: rewriting a live, tested, playing round to gain nothing is a bad trade. It stopped being right the moment a day had to hold three challenges, because the alternative was a *second* implementation of ordering, throttling and per-challenge timing beside the one tournaments already had under test. Three consequences are worth knowing. **FR-2.3's 180-day no-repeat window had to go**: at three countries a day it is arithmetically impossible (540 draws from a pool of 196), replaced by 120 days per kind plus 30 days for any kind. **A day is now worth 0–18 where history holds 0–6**; the 7- and 30-day windows heal within a month and the all-time column keeps a seam, which is cheaper and more honest than rewriting what people already played (Paulo's call, 2026-09-10). **The attempt document keeps `guessCount`, `solved`, `points` and `elapsedMs` at its top level** even though the detail moved into `items`, because that is the shape pre-D-52 attempts have — so the nightly job and the dashboard read both generations with no migration and no branch. |
| D-53 | **`gdp` asks for GDP per capita, PPP, in current international dollars, for one pinned year shown in the prompt (World Bank, CC BY 4.0). A guess within 10 % — stated as `min/max >= 0.9` — is simply correct, on the usual `[6, 4, 2]` ladder.** | Answers OQ-12. Per capita PPP beat the three alternatives on **spread**, which is the only thing that makes a number guessable: 133× from Burundi to Luxembourg against 520 000× for total GDP, which is really a population quiz. PPP also keeps the figure still between vintages, where nominal moves with exchange rates. 2023 over 2024 for one more country and because the World Bank has largely finished revising it. The banded scoring 06-tournaments.md sketched — 10 % → 6, 25 % → 4, 50 % → 2 — was dropped: it needs a per-kind score function, and it would make `gdp` the only kind that pays for a near miss, when a silhouette guessed 200 km out already scores what one 10 000 km out scores. The cost that was real: `StoredGuess` became a union, `Kind` gained `wasCorrect` so the share grid can read a finished guess back without a clock, and the callables stopped validating guesses because only the kind knows what a guess is. |
| D-54 | **The `gdp` prompt, the guess field, the guess rows and the reveal all state the unit: `US$`.** | From the first session with real players, 2026-09-11. The figure was *always* in international dollars — `NY.GDP.PCAP.PP.CD` is "current international $" — and the only place that said so was `regras.html`, which nobody reads before the first question. Players read a bare `20.868` as reais, which is off by roughly five times: not a hard question, an unanswerable one. Switching the indicator to **nominal** USD was considered and rejected: it would silently change the answer of every already-seeded future day under a live game, widen the spread D-53 chose the metric for, and reverse half of D-53 to fix what is a labelling bug. The residual is stated rather than hidden — a player who searches finds the nominal figure and is still wrong — and the help popup (D-56) is where that is said, because it is the one text a player is made to read. |
| D-55 | **A challenge ends on a reveal the player dismisses, not on an automatic jump to the next prompt.** | Same session: "users want to read the result before going to the next challenge". The old flow overwrote `round` and re-rendered on the same frame, so the answer to the challenge just played was on screen for no frames at all. Built entirely client-side and deliberately not persisted: the server already reveals a finished challenge's answer in `items` (SEC-1 permits it — that challenge is over), so this needs no new field, no new state and no migration, and a reload legitimately lands on the next challenge. One field was needed after all: `items[i].guesses`, non-null only once that challenge is over. `RoundView.guesses` is always the *current* challenge's, so the decisive guess — the one that solved or exhausted the challenge — was in no list the client held, and a reveal built from the screen's stale list showed every guess *except* the one that mattered. Caught by playing it, not by a test. A solve also gets confetti: ~30 lines of DOM and one keyframe, not a dependency, and off entirely under `prefers-reduced-motion`. |
| D-56 | **The "?" explains the hints of the challenge on screen, and forces itself open the first time — once per hint *vocabulary*, not once per kind.** | Same session: "they did not understand the percentage very well". Two texts cover four kinds, because shape, flag and capital all answer with a country and so all give kilometres, a compass arrow and a proximity percentage, while `gdp` gives higher/lower and a ratio. Four popups to teach two vocabularies is three too many. It opens itself because a "?" nobody presses explains nothing, and the people who gave this feedback had the guess rows in front of them for a whole session. Remembered in `localStorage`, per browser, wrapped in `try`/`catch`: where it throws the dialog simply introduces itself again, which is the harmless failure. Neither text names a real country's figure — a static string that did would be the answer to that country's `gdp` challenge (SEC-1). |
| D-57 | **A desktop layout that is purely additive: one breakpoint at 60rem, the phone layout untouched below it, and the width a wide screen has spare spent on *information* rather than on rearranging the game.** | Paulo, 2026-09-12, after the first real-user session: the frontend "looks like it was built for a phone", but the game screen itself "is the only screen that is fairly good". So the game column is not touched — same elements, same order, same 30rem — and `#game` simply becomes a two-column grid whose second column carries the group's "Hoje" and the player's streak. The card gets the same treatment with the open round's players, because playing a card is the loneliest screen in the app. Three things make this safe rather than a rewrite. **Every rule of the desktop layer lives inside the media query**, so under 60rem the computed style is what it was — verified by rule, not by care. (Four rules *do* sit outside it, and none of them are the desktop layout: measuring at 360px turned up four pre-existing horizontal scrollbars — the nav with six items, the scoring table on `regras.html`, and a running tournament's card and its meta line — all fixed by letting things wrap or scroll inside their own box. FR-6.1 had only ever said "works down to 360px"; it now says "and does not scroll sideways", which is the clause those four were quietly failing.) **No document order changed**, on any page: `grupos.html` keeps its children exactly where they were, and `torneios.html` keeps `#round` first in the DOM (where a phone wants it) and moves it with `grid-column` instead. **The panels are never on the critical path**: `listGroups` and `getTournament` are fired in the same tick as `getRound`/`getCard` and never awaited by the game, a failure leaves the panel hidden, and nothing in a panel may write `#status` — a side list that cannot load must never tell a player their game is broken. The panels are hidden rather than stacked below 60rem: the same information is one tap away on `grupos.html`, and "keep the phone view as it is" was the instruction. |
| D-58 | **`RoundView.me` carries the streak counters, and `submitGuess` returns the profile its own guess just wrote.** | The panel shows a streak, and the streak's whole moment is the guess that ends the day. `submitGuess` returned `me: null` and would have shown the new number on the next reload — right in the data, wrong in the experience. The profile was already read inside that transaction and `recordCompletion` already wrote it there; only the return value changed, so this costs no reads. The four counters ride along on a profile both doors already load. |

The first lock — `buildOptions` excluding every other subject on the card — was always the one doing the work, and the rule it replaced even cited it as the reason. It is now **load-bearing alone**, so it is pinned three times instead of once: per card (`card.test.ts`, 200 mixed cards), per call (`kinds.test.ts`, `buildOptions` honours its exclusion set), and **across a generated year of 730 daily boards** (`tools/lib/schedule.test.mjs`, the new one). **A consequence accepted rather than fixed**: FR-2.3 constrains subjects by kind and says nothing about distractors, so today's distractor may be tomorrow's subject — a player taught Peru's flag on Monday may be asked for it on Tuesday. That is not a leak, because a flag is a public fact and Tuesday's secret is still which tile; it is the feature working. **The type was collapsed on the way through**: `{ code, name, pick? }` was restated in `kinds.ts`, `round.ts`, `card.ts` and `practice.ts`, so adding one field meant four edits and three chances to miss one. It is now `Reveal`, exported once and imported three times. |
| D-78 | **A seventh kind: `person` — "onde nasceu {pessoa}?", from Pantheon and Wikimedia. Practice and a tournament preset, NOT the daily.** | Paulo, 2026-09-24: "this will help users learn more about each country… we should only show people that were born in countries that we have data for". The kind itself is nearly free: the answer is a typed country, so `gradeCountryGuess`, the rhumb compass, the proximity bar and `capital`'s 6/4/2 ladder are all reused, and what is new is a pool, a prompt with a photograph in it, and `tools/build-people.mjs`. Four decisions are not free. **The photograph is hotlinked from Wikimedia Commons** rather than vendored — Paulo's call, against a recommendation of public-domain-only and shipped bytes: nothing enters the repo and no licence is exercised by redistribution, and the price is that a player's browser talks to a third party, which `privacidade.html` now discloses, and that a challenge has to stay playable when the photo does not arrive. **The person is stored on the card**, which is FR-8.7's argument applied to something that is not an option: a rebuilt `people.json` reorders a country's list, and a face derived on read would change between two guesses. **The answer is the country the place is in TODAY** — Kant is Rússia, Marie Curie is Polônia — said in the help and in `regras.html`, with the birth city shown at the reveal so the answer teaches instead of tricking; it is D-67's shape of accepted cost, written down rather than patched. **And the leak surface is text, not pictures.** A portrait gives nothing away; the three strings beside it do. Pantheon's `description` reads "Turkish actor and fashion model" and never enters the build, the birth city belongs to the reveal, and the guard that rejects a name or filename naming the country had to grow twice while the build was running — once for adjectives, because "brasileiro" is not "Brasil", and once for the **credit**, where the Emirates' most famous man turned out to be photographed by the "Dubai Government Photographer". `tools/people-aliases.json` handles what a country is called without being named, **keyed per country on purpose**: "Isabel I de Inglaterra" is Reino Unido written out, while "Catarina I da Rússia" was born in Estonia and is exactly the question this kind exists to ask. **Measured, not estimated**: 174 of 196 countries field at least one usable person. |

## 8. Privacy posture

Players use personal emails, which lowers the corporate-policy stakes but does not remove
LGPD obligations — you are still a controller of personal data about identifiable people.

Rules:

- Collect only: Firebase `uid`, email (from the auth provider), chosen display name, game results.
- **Display name is user-chosen and defaults to a random generated handle**, never the email
  local-part and never a real name. The leaderboard must not become a de-facto staff directory.
- Email is never displayed to other users, ever. Not in groups, not in challenges.
- A working account-deletion path must exist before you share the link with anyone (Phase 2).
- A one-page privacy note lives at `/mondo/privacidade.html`: what is stored, why, how to delete.
- Give whoever owns security policy at the company a heads-up before sharing. Ten minutes of
  conversation now beats an awkward conversation later.
